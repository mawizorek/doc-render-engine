# form picker: one generic form, every program in a menu

🚫 **Claims no build number, deliberately** (see `next-build-spec.md`). ✅ **BUILT
2026-10-12.** Scoped, ruled and built in one pass, which §7 argues was the right
call and §8 prices. Arguments and the road not taken:
[`docrender/formpicker-dl.md`](../docrender/formpicker-dl.md).

> Michael, 2026-10-12: *"would there be some way for us to generate a passive
> version of the embedded generic program submission form that we have - but we
> append the completed program(s) via a separate page object (think custom popup
> of available program forms generated from a specific registry - either
> autogenerated or hand maintained) so we could make a custom 'Submit completion
> of any program' type of page and using a repo source to generate the popup
> values to append to the embedded form url?"*

## §1 What it is

One page. One embedded ClickUp form. A `<select>` listing every program this site
builds, and picking one rewrites the form's `?Program_ID=` in place.

    ---
    id: page-record-completion
    title: Record a program completion
    type: page
    status: unlisted
    forms:
      completion:
        src: https://forms.clickup.com/36074068/f/12cwjm-53753/32FA65B2LAOIHP1NR5?Program_ID=ITPSAFE-1336
        text: Program completion form
    ---

    # Record a program completion

    !!! formpicker "completion"

⭐ **NO NEW FRONTMATTER.** The page declares a form the way every program page
already does; the directive is the only new vocabulary.

## §2 Who it is for, which decided everything else

> Michael, 2026-10-12: *"just a staff quick link (mostly me) i put form for any
> student completing a form"*

A STAFF surface, not a learner one. A student who just read a program already has
its form at the bottom of that page; this exists for in-person and paper
completions and for retroactive entry, where the person doing the typing is not
the person who did the training.

⚠️ **THAT IS WHY THE PAGE IS `status: unlisted` AND WHY NOTHING PREFILLS THE
STUDENT.** The form's own fields carry who completed it, and a second place to
type a name would be a second claimant on the one fact the record exists to hold.

## §3 Rulings

**F1 · The menu is DERIVED from the build, never declared.** No `programs:` key,
no registry file, no list anybody maintains. Every program page already states its
own `Program_ID=` inside its `forms:` src. 🚫 A hand-kept list is the defect that
retired `roster.json`, `registry.json` and `app-index.md`. Michael offered
*"either autogenerated or hand maintained"*; the house rule answers it.

**F2 · Membership is "carries a `Program_ID=`", which is Michael's rule verbatim.**
*"form ids only exist once they have a real canonical clickup program id"* — so a
parameter found in the build is proof of a canonical ClickUp program, and nothing
here has to consult ClickUp to know it. ⭐ This collapsed the repo-versus-canonical
fork rather than answering it (dl D3).

**F3 · Published pages only, by construction.** The gate is `id in state.PAGES`,
the map built after visibility prunes, so a draft program cannot leak its title
into the menu. 🚫 Not a filter over `BY_SRC` — a filter would imply the unpublished
entries were ever candidates.

**F4 · A Program_ID claimed twice is won by `type: program` and reported either
way.** 🔴 NEVER by filename order, which was the first version's behaviour and made
ownership depend on a path (dl D6). Two real programs sharing an id fall back to
walk order and are reported loudly; that is the borrowed-id bug, and no automatic
rule should quietly resolve it.

**F5 · The frame is `forms.py`'s.** The picker renders a `<select>` and delegates
to `forms._html`. 🚫 No second iframe renderer: that file carries the scroll-window
rule, the zero-height trap, and print rules WeasyPrint cannot see. 🚨 Delegation
means inheriting forms' three page-level assets by hand, gated on absence — the
bug this introduced and the tests caught is dl D4a.

**F6 · A base with no `Program_ID=` gets NO MENU, and that is a refusal.** The swap
rewrites an existing parameter and will not append one. Rendering the control
anyway is a dead control: every pick fires and nothing changes.

**F7 · Swap by `cloneNode` + `replaceWith`.** Never `iframe.src =`, which pushes a
session-history entry so Back walks iframe states. Same ruling as the Reload
button.

**F8 · It fails open to a real, working form.** With JavaScript off the page is the
declared default program's form, submittable and correctly attributed. ⭐ The
fallback anchor is retargeted on every pick, because it is the control that works
when the frame does not.

**F9 · The select is hidden on paper; the SELECTION is not.** A dropdown prints as
a grey box saying nothing. The line naming the chosen program is the only part of
this control that means anything once printed.

**F10 · Sorted by title.** Sorting by Program_ID would order the menu by the
accident of when each task was created in ClickUp.

## §4 OUT, by name

1. A `programs:` key or any declared list (F1).
2. Appending a `Program_ID` to a base that lacks one (F6).
3. Reading the canonical ClickUp **Programs (canonical)** list. That is
   `clickup-mirror.md`'s territory.
4. Prefilling the student (§2).
5. Grouping the menu by site, department or binder. One flat list until somebody
   measures that it is hard to scan.
6. Cross-site menus. Chains and builds are per site; so is this.
7. The `forms:` site-wide rung — see §6, which is the interesting refusal.

## §6 The second half of the ask: scoped, NOT built, and the fork named

> Michael, 2026-10-12: *"also like image media, I wonder if we could supplement
> local form definitions for a single registry of available REPO forms so i don't
> have to find the same link throughout. but that's kinda a tangent maybe?"*

Not a tangent — the same feature one layer down. But the obvious build does NOT
solve the pain he named, and that is why it is here rather than in §5.

**What exists:** `links:` already has two rungs, `instances/<slug>/site.yml` for
the site-wide registry and page frontmatter for a local override, with the page
winning and the override reported out loud (`urllinks.py`). `forms:` has only the
page rung. `qr.py` already walks page `links:` → `site.yml` → page `forms:`, so
cross-registry resolution has precedent.

🔴 **AND GIVING `forms:` THE SAME SITE RUNG WOULD BUY ALMOST NOTHING.** A site-wide
`forms: completion:` entry is inherited by pages that declare no `forms:` block —
but every program page needs its OWN `Program_ID`, so none of them can inherit it.
The repeated string is the base URL, and the varying part is the parameter.

**So the real fork, which Michael has not ruled:**

**Option A · the site rung alone.** Cheap, precedented, and only helps pages that
want the whole URL unchanged — which is approximately only the picker page itself.

**Option B · compose from a `program_id:`.** `site.yml` holds the base once; a
program page writes `program_id: ITPSAFE-1337` and the engine composes the src.
This is what actually stops him hunting the link. ⚠️ It is a schema change on every
program page plus a content migration, it needs a precedence rule against an
explicit `src:`, and it puts a THIRD spelling of "where is this program's form"
into the vocabulary until the migration finishes.

⚠️ **B is the one worth building and it is not a fold-in.** Recorded unbuilt rather
than guessed at, because picking B silently would have migrated every program page
on two sites inside a build that was scoped as a page control.

## §7 Why this shipped without a separate spec pass

Michael ruled *spec and build in one pass*. ⭐ It held because §3's rulings are all
inherited: F1 is the retired-manifest rule, F5 and F7 are `forms.py`'s existing
traps, F3 is `state.py`'s own distinction, F9 is the print-rule law. **Only F2,
F4 and F6 are new, and F2 is a quote.** ⚠️ F4 and F6 were both WRONG in the first
working version and were corrected by tests, not by review — which is the honest
argument for a sandbox pass, not for a spec pass.

## §8 Not verified

- 🔴 **No MkDocs build was run, and the delegation to the real `forms._html` is
  therefore untested.** The suite reproduces the four symbols this module imports
  with the same signatures (the real file cannot be copied under the read ceiling),
  so what is proven is the catalog, the markup, the refusals and the asset
  inheritance against that contract. **First real run = next publish.**
- The URL swap was proven in `node` against six real shapes (`?Program_ID=` first,
  mid-query, with a fragment, empty, and absent). `node --check` passes on the
  inlined listener. ⚠️ **No browser run.**
- ⚠️ **Print is unverified and is the likeliest thing to be wrong**, for the reason
  `forms.py` records: WeasyPrint discards `display: revert` as invalid, so the
  harness passes while Chrome prints the control. Reproduce in Chrome.
- Nothing proves a Program_ID is still LIVE in ClickUp. A retired program keeps
  rendering a confident option.
- ⚠️ **No picker page exists yet on any site.** The directive has no live caller
  until Michael adds one, and `uritp-safety` is where the Program_IDs live.
