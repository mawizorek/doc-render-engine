# `formpicker.py` -- the arguments

The warnings live in `docrender/formpicker.py`. This file holds WHY each one
exists. Same split `forms.py`/`forms-dl.md` and `views.py`/`views-dl.md` use, and
for the same measured reason: `forms.py` crossed the 22,528 B read ceiling four
times while reasoning was written into it, and a file past the ceiling cannot be
read whole, so it cannot be safely rewritten.

Scoped and built 2026-10-12. Spec: [`specs/form-picker.md`](../specs/form-picker.md).

## D1 · The ask arrived describing a registry, and the registry was already there

> Michael, 2026-10-12: *"would there be some way for us to generate a passive
> version of the embedded generic program submission form that we have - but we
> append the completed program(s) via a separate page object (think custom popup of
> available program forms generated from a specific registry - either autogenerated
> or hand maintained)"*

The request names its own mechanism: a registry of available program forms, and a
control that appends a value to an embed URL. ⭐ **Both halves already existed and
neither needed inventing.** `forms:` has been a registry since 2026-08-19, and
every program page has carried its own `?Program_ID=` inside that registry since
the parameter became the record. What was missing was a reader.

⚠️ This is the second time that general form has been worth writing down.
`urllinks.py` records the first: an ask that arrived *"carrying its own
workaround"* (a second sigil, to dodge a collision that could not happen), where
the correct answer was to price the workaround against the mechanism already in
the repo. Here the workaround was the word *"hand maintained"*.

## D2 · "either autogenerated or hand maintained" -- the house answers this one

DERIVED, and not as a preference. A hand-kept list of programs would be a second
place stating which programs exist and what each one's Program_ID is, with
nothing reconciling it against the pages that already state both. 🔴 That is the
shape this repo has retired `roster.json`, `registry.json` and `app-index.md`
over, and the one `next-build-spec.md` refused a row count for in its own opening
paragraph.

⭐ **AND THE DERIVED VERSION IS STRICTLY MORE USEFUL, WHICH IS THE PART WORTH
KEEPING.** A hand list cannot notice that two pages claim one Program_ID. The walk
can, and does, and that exact bug has already bitten this workspace three times:
`program-general-safety-rehearsals` borrowed ITPSAFE-1242 (Scene Shop), then
1225 (General Safety for All), before 1335 was created for it; the Emergency
Handbook borrowed 1242 as well before 1336; FOH Safety got 1337 new. ⚠️ A hand
registry would have recorded each borrowed id as fact.

## D3 · Michael's membership rule did the hardest part of the design

> Michael, 2026-10-12: *"form ids only exist once they have a real canonical
> clickup program id"*

This is what makes the menu DECIDABLE without a second authority. The open
question before it was which side ruled: the repo (only programs that have pages)
or the canonical ClickUp **Programs (canonical)** list (every program, some
without pages). ⭐ **His rule collapses the fork instead of answering it.** A
`Program_ID=` cannot be written into a page until the canonical program exists, so
a parameter found in the build is proof of a canonical program. The repo walk
cannot invent a program, and nothing here has to check ClickUp to know that.

⚠️ **THE REVERSE DIRECTION IS STILL OPEN AND IS NOT A DEFECT YET.** A canonical
program with no page cannot be offered. Michael authors both, so the gap is a
worklist item rather than a leak -- but it is the one thing that would push this
build toward reading ClickUp, and `specs/clickup-mirror.md` is where that would
have to be argued.

## D4 · Why the frame is borrowed and the menu is not

`forms._html` carries an unusual density of hard-won traps: the scroll window is
the WRAPPER and never the frame (capping the iframe clips ClickUp's form app
instead of scrolling it), `height="100%"` with no sized parent renders ~0px tall,
every print `display` rule has to be `!important` because `print-flow.css` sets
`display: revert !important` on `<details>` children, and WeasyPrint cannot see
that bug at all so the print harness passes while Chrome prints the whole form.

🔴 **A second iframe renderer would have had to re-derive every one of those, and
would have gotten the WeasyPrint one wrong, because the test that would catch it
passes either way.** So the picker renders a `<select>` and calls `forms._html`.

⭐ `views.py` set this precedent by importing `_esc` and `_dead` from `forms.py`,
with the argument stated there: *"two copies of a failure vocabulary is how they
start disagreeing about what broken looks like."* Borrowing the whole frame is the
same argument one size up.

### D4a · The bug that delegation introduced, and that the tests caught

🚨 `forms.on_page_markdown` appends the CDN height script, the print CSS and the
Reload listener **gated on its own pass having matched something.** A page whose
only embed came from a picker matched nothing in that pass, so the first working
version of this module shipped a frame with no dynamic height, no print rules and
a Reload button bound to nothing. ⚠️ **Two of those three are invisible on
screen.** The height one degrades to a 40rem clipped form, which reads as "the
form is a bit short"; the print one only shows up on paper, in Chrome, and the
harness that would check it is blind to the rule.

`_inherit` appends whichever are absent, tests for presence so a page carrying
both directives gets one copy, and keeps the three gates SEPARATE -- the height
script needs a ClickUp frame, the print rules need any frame, the listener needs a
button. 🔴 Collapsing the last two is a bug `forms.py` has already shipped once:
the print rules rode in the reload-button block, so a page setting `reload: false`
printed its entire iframe.

## D5 · Two refusals, both of them the same rule

**A base with no `Program_ID=` gets no menu.** The swap rewrites an existing
parameter and does not append one: appending would have to guess `?` versus `&`,
and would still leave the arrival state unattributed. ⚠️ The first version
rendered the `<select>` anyway. It looked perfect and did nothing -- every pick
fired, nothing changed, nothing in the report. 🔴 That is the dead control this
engine kills on sight, and it was caught in the sandbox by running the swap regex
against six real URL shapes rather than by reading the code.

**A dead slot passes straight through.** `forms._html` already rendered the
struck-through span and filed the finding. Wrapping a menu around a form that does
not exist offers a control that cannot work, and would also bury the diagnosis.

## D6 · The collision tiebreak was wrong first, and filename order is why

The first version kept whichever page the sorted `BY_SRC` walk reached first. 🔴
**That makes ownership of a Program_ID depend on a file PATH** -- something no
author thinks about, and which the report could not explain because the report
would have been telling the truth. A test written to assert the obvious answer
(the FOH program owns the FOH form) failed, because `clone.md` sorts before
`foh.md`.

⭐ **`type: program` is the tiebreak, and it is principled rather than a patch.** A
program page owns its own completion form; a page that merely embeds one is the
interloper. Two REAL programs sharing an id still fall back to walk order, and
that case is reported loudly -- it is the borrowed-id bug from D2, which no
automatic rule should silently resolve.

## D7 · Unpublished pages, and why membership is `state.PAGES`

The catalog reads `state.BY_SRC` for frontmatter but gates on the page's `id`
being in `state.PAGES`, which is the map built AFTER visibility prunes. ⭐ So a
draft program cannot leak its title into a staff menu, and that is by construction
rather than by a filter -- the same distinction `state.py` draws about `REFS`,
where hidden pages are absent because the event never runs for them and *"a filter
would imply otherwise."*

## D8 · What was deliberately not built

1. **A `programs:` key, a `registry.json`, or any declared list.** D2.
2. **Appending a `Program_ID` to a base that lacks one.** D5.
3. **Reading the canonical ClickUp list.** D3; that is `clickup-mirror.md`'s
   territory.
4. **Prefilling the student.** Michael submits these himself and the form's own
   fields carry the person. A second place to type a name is a second claimant on
   who completed the program.
5. **Grouping the menu by site, department or binder.** One flat list sorted by
   title until the list is long enough to be hard to scan, which is a measurement
   nobody has taken.
6. **The `forms:` site-wide rung.** Scoped in `specs/form-picker.md` §6 and NOT
   built, because it does not solve the pain Michael named -- see that section.
